# 设计方案：项目启动器与多 Agent 对话记录管理器

> 本文件是项目最初的设计方案（由需求方与执行 AI 共同确认），保留在仓库里用于说明
> 功能边界与验收标准。**当前实现以 README 为准**：本方案描述的是第一版范围，
> 实现过程中个别细节已按实测调整（例如增量扫描的来源判定、Markdown 往返格式）。

- 目标平台：Windows 桌面优先
- 数据策略：本地优先，可选导入导出
- 首版交付：可运行源码、Windows 开发启动方式、可打包的便携版或安装包

## 1. 目标

开发一个 Windows 桌面启动器，把个人开发项目、常用软件、CLI 工具和 Agent 入口集中到一个应用中，提供搜索、配置和快捷启动能力。

同时统一管理以下 Agent 的启动入口和对话记录：

- Qoder CLI
- Qoder CN
- MiniMax CLI
- MiniMax 桌面端
- Codex 桌面端
- Codex CLI
- Trae 桌面端

对话记录要能导入已有历史，并在记录来源稳定可读时持续做增量扫描。用户可以先按 Agent 切换，再按项目查看对话；无法归入登记项目的记录进入“未分组”。

## 2. 首版范围

### 2.1 必须实现

1. 启动项管理：普通应用、CLI 命令、项目目录。
2. 启动项的新增、编辑、删除、启用/禁用、搜索和启动。
3. 项目登记：项目名称、根目录、可选启动配置。
4. 对话记录导入、展示、搜索、排序和项目归组。
5. Agent 适配器架构，至少覆盖上面列出的 8 个入口。
6. 本地 SQLite 存储和迁移。
7. JSON/Markdown 导入导出。
8. Windows 开发运行和可打包交付。
9. 自动化测试、Windows 构建/运行验证和能力矩阵。

### 2.2 明确不做

- 云端同步和账号体系；
- 向外部 Agent 发送消息；
- 修改或删除 Agent 原始历史文件；
- 移动端；
- 语义搜索、标签、统计等高级功能；
- 在没有证据时假设某个 Agent 存在公开 API 或固定路径。

## 3. 技术方案

首选 Electron + React + TypeScript。界面与数据采集、进程启动分离：

- Electron 主进程：启动外部程序、访问文件系统、数据存取、扫描任务；
- React 渲染进程：启动页、项目页、对话记录页、设置页；
- IPC：只暴露明确的受控接口；
- SQLite：本地持久化，带迁移机制；
- 文件扫描：可使用文件监控或周期性扫描，具体库由实现方选择。

如果执行环境证明 Electron 无法完成 Windows 打包，允许改用 Tauri 或 .NET，但必须保持本方案的数据模型、功能范围、验收行为和本地优先策略不变，并在交付材料中说明原因和影响。

所有 CLI 启动必须使用可控的程序路径、参数数组和工作目录，不能把整条用户输入直接拼接成 shell 字符串。

## 4. 启动项与项目模型

### 4.1 启动项

启动项至少包含：

- 唯一 ID；
- 显示名称；
- 类型：app、cli、project；
- 可执行文件或命令；
- 参数；
- 工作目录；
- 关联项目（可选）；
- 图标或图标路径（可选）；
- 启用状态；
- 最近启动时间；
- 创建和更新时间。

启动失败时显示可理解的错误，包括找不到程序、工作目录不存在、权限失败和退出码。

### 4.2 项目

项目至少包含：

- 唯一 ID；
- 名称；
- 根目录；
- 可选启动项；
- 创建和更新时间。

自动归组规则：

1. 使用记录来源的 cwd、来源路径或适配器提供的项目路径；
2. 与已登记项目根目录匹配；
3. 多个项目匹配时取路径最长、也就是最深的项目；
4. 无法匹配时放入“未分组”；
5. 用户手动调整后保存覆盖关系，重启和重新扫描后仍然有效。

## 5. 对话记录统一模型

每条会话至少保存：

- 唯一 ID；
- Agent 标识；
- 外部会话 ID（如有）；
- 标题；
- 创建时间和更新时间；
- 消息内容；
- 来源文件或来源位置；
- 来源 cwd/项目路径（如有）；
- 原始元数据；
- 导入指纹；
- 自动归组结果；
- 人工项目覆盖关系。

导入必须去重。相同来源文件、外部会话 ID 或内容指纹不得在重复扫描后生成重复会话。原始 Agent 文件只读，应用不回写。

## 6. Agent 适配器

每个适配器负责：

1. 启动配置；
2. 记录来源发现或用户自定义来源路径；
3. 首次导入；
4. 解析和归一化；
5. 去重；
6. 增量扫描；
7. 能力状态和错误原因。

能力状态至少区分：

- launchable：可启动；
- importable：已验证可导入；
- watchable：已验证可增量扫描；
- needs_config：需要用户配置来源路径；
- unsupported：当前环境或格式无法验证。

所有 8 个入口必须可配置和可启动，记录能力按实际验证结果列出。Qoder CN、桌面端 Agent 等产品如果没有稳定可读的本地记录，应显示明确原因，并提供通用 JSON/Markdown 导入，不得声称已经自动同步。

实现方需要先探测实际机器上的安装情况、可执行路径和记录来源，再实现适配器；不能凭产品名称猜路径。对于不便在当前机器验证的格式，必须使用脱敏 fixture 做解析测试，并把 fixture 验证和真实机器验证区分记录。

## 7. 界面要求

主导航至少包含：

- 启动；
- 项目；
- 对话记录；
- 设置。

启动页：搜索启动项、最近使用、一键启动、启动失败反馈。

管理页：新增、编辑、删除、启用/禁用；三类启动项表单；可选测试启动。

对话记录页：按 Agent 切换；项目列表和固定的“未分组”；会话列表；标题和正文关键词搜索；创建/更新时间排序；详情阅读；来源元数据；手动调整项目归属；手动重新扫描。

设置页：Agent 来源路径；发现结果和能力状态；扫描状态与失败原因；导入 JSON/Markdown；导出 JSON/Markdown；本地数据目录和备份入口。

## 8. 数据导入导出

必须提供稳定的内部 JSON 格式，至少包含版本号、Agent、会话元数据、消息内容和项目归属。

Markdown 导入至少支持标题、时间、Agent、项目和消息正文。

导出后应能在另一个空数据目录中重新导入，并恢复内容、Agent 和项目归属。导入格式需在 README 中给出最小示例。

## 9. 开源参考

需要实际检查至少两个成熟的开源本地对话产品，可从 Cherry Studio、Chatbox、Jan 等项目开始，重点参考会话列表和详情布局、项目/分组结构、本地数据保存、导入导出、空状态和错误状态。

交付材料必须列出实际参考链接、许可证和具体借鉴点。只借鉴交互和公开设计，不复制不明来源代码。

## 10. 验收标准

### A. 构建与运行

- 在干净 Windows 环境按 README 可启动开发版；
- 能生成可运行的便携版或安装包；
- README 写清 Node/包管理器/构建依赖和命令；
- 首次启动不依赖网络即可查看已导入数据。

### B. 启动器

- 三类启动项都能新增、编辑、删除、禁用和启动；
- 启动项搜索和最近使用可用；
- 启动失败有明确错误；
- 8 个指定 Agent 入口均有启动配置；
- 当前环境未安装或无法验证的入口有清晰状态、配置方法和原因。

### C. 项目与归组

- 可登记、编辑、删除项目；
- 自动归组按路径最长匹配；
- 手动归组重启后仍保持；
- 未匹配记录进入未分组。

### D. 对话记录

- 可导入至少一组真实记录或等价 fixture；
- 重复导入不会产生副本；
- 可按 Agent 切换；
- 可按项目/未分组筛选；
- 可搜索标题和正文；
- 可按时间排序；
- 可阅读详情和来源元数据；
- 可导出并在空数据目录重新导入；
- 对可解析来源，新增记录经增量扫描后出现；
- 对不可解析来源，显示真实限制并提供通用导入。

### E. 工程质量

- 有数据模型、去重、项目归组和至少两个适配器解析器的自动化测试；
- 有一次 Windows 构建/运行和核心流程验证；
- 代码中没有把用户输入直接拼接进 shell 命令；
- 交付材料列出完成项、Agent 能力矩阵、未完成项、重要自主决策和已知限制；
- 无法验证的内容必须如实说明。

## 11. 返工策略

按一次完整实现加一次集中修正控制成本。

如果某个 Agent 的真实格式不可获得：

1. 保留其启动能力；
2. 提供配置来源路径和通用 JSON/Markdown 导入；
3. 在能力矩阵标记为 needs_config 或 unsupported；
4. 提供 fixture 解析测试（若格式已知）；
5. 明确不能验证自动同步。

如果同类错误反复出现、修正破坏已通过模块，或执行方无法完成 Windows 运行验证，应停止无效重试，转由方案负责人接手局部修复或重新划分范围。
